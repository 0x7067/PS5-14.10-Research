# Cross-firmware pattern research: 13.60 evidence for 14.10 leads

Updated 2026-10-17. This is static analysis of the local 13.60 captures correlated with the saved 14.10 probe logs. No 14.10 kernel image is present, so 13.60 handler behavior below is a source-derived hypothesis, not a claim about identical 14.10 code.

## Evidence quality and inference boundary

The local 13.60 capture includes 15,132,096 bytes of kernel text-prefix data, 4 MiB of kernel data, a separate 64 KiB sysent-region capture, all 145 handler samples for syscall numbers 532–676, and a parsed 679-entry syscall table. The text/data/sysent failmaps report zero failed chunks. The sysent table is 32,592 bytes, exactly 679 × 48, and the sysent bytes in `sysent_area.bin` match `sysent_raw.bin`.

The Sony table index contains 311 non-`nosys` entries overall, 115 non-`nosys` handlers in 532–676, and 30 `nosys` stubs in that range. The earlier README statement of 117 real Sony handlers is inconsistent with the captured index and must be corrected. Entries 677–678 are malformed in `narg` and excluded.

There is no local 14.10 kernel text or sysent capture. Therefore handler names/identities and behavior inferred from 13.60 are only transferable hypotheses. Also, each `handler_NNN.bin` is a 4 KiB window beginning at the resolved handler address; it is not a complete function dump when the function exceeds that size.

## What Relapse contributes

Public Relapse research identifies two linked 13.60 prerequisites: an AF_ROUTE response used to defeat KASLR and the `aio_multi_wait` UAF used to obtain kernel R/W. Probe 43o's RTM_GET write failed, and its read returned 108 bytes with zero detected pointers and unresolved attribution; a valid route-disclosure test is not established. Probe 43p's saved output stops after announcing standard `aio_error` (317), so it does not establish that call's result and does not reach the planned Sony syscall scan. In particular, syscall 663 (`aio_multi_wait` in the public Relapse mapping) has no 14.10 test result in the repository. Therefore, the existing artifacts do not establish whether this Relapse path is blocked at the syscall, although public notes report the vulnerability patched at 14.00. The AIO-related handlers remain distinct from a demonstrated new exploit.

The 13.60 local table and public Relapse documentation independently place the candidate `aio_multi_wait` at syscall 663. Its 13.60 entry has five arguments and wraps the implementation at TEXT+`0x3b0210`. Treat this as a strong identity mapping for 13.60, not proof of the 14.10 table or handler semantics. Avoid inferring any other number’s function from a different firmware’s table alone.

## Ranked research tasks from existing artifacts

1. **Repair evidence metadata.** Rebuild the Sony syscall name map from the captured sysent table and handler analysis. Current `ps5_13.60_sysent.json` omits active entries 515/619/635, includes malformed 677/678, and its counts disagree with the binary index.
2. **Explain 624 precisely.** Its 13.60 code is a scalar VM-state read, which matches the 14.10 small integer. The planned 52b probe is in `probes/phase13_52batch/52b_624_oracle.lua`, but no saved 52b output exists. If a future console session is available, the single most discriminating low-risk check is: read 624 repeatedly at baseline, map and touch a known number of pages, read again, unmap, then read again; report every value and the mapping operation result. A reproducible delta tracking that process’s map would support a process-local VM metric; stability or unrelated changes would weaken that hypothesis. This test still would not imply a kernel pointer disclosure.
3. **Map the active process family 563–566 and VM pair 548/572.** Recover full function boundaries from the 13.60 text capture, call graphs, constants and argument structures. The available 51a log reports 563–566 and 572 returning zero for zero-argument calls (even though the wrappers declare arguments); treat that as a weak default-path observation, not evidence that those calls are generally usable. Compare against the already saved 14.10 behavior; keep hypotheses separate where prototypes are not established.
4. **Trace the 593/596 dynlib family.** 593 already leaks userland module bases; 596 is a separate stateful handler. Identify shared helpers, lock scope, output-copy paths, and whether the 14.10 probe outputs show any affected state. Do not equate module-base disclosure with kernel KASLR defeat.
5. **Corrected AIO coverage.** Current 51c raw output records only 625/626. Current 43p raw output stops at its first ordinary AIO call, syscall 317; its phase-4 532–700 scan was never reached. Treat 663 as untested on 14.10, and don't infer results for 661–670 from the missing tail. A 14.10 test would be a deliberate kernel-risk experiment and should not be performed on the user's only retail console as a prerequisite for static research.
6. **Use firmware evidence if available.** Publicly documented 14.00 patch boundaries and the 13.60 disassembly can prioritize changes, but only a 14.00/14.10 code artifact can establish whether a particular branch was added, removed, or retained.

## Bottom-line inference

The most defensible result is that the AIO-family implementation at 663 is statically present in the 13.60 capture, while the repository's 14.10 probe logs do not test it. This fixes a coverage error; it is not a new exploit finding. More broadly, Sony VM/process/AIO/dynlib handlers provide concrete static-analysis targets, but there is no demonstrated 14.10 kernel R/W primitive in the saved evidence. See [the 13.60 secondary exploit audit](SECONDARY_EXPLOIT_AUDIT_13.60.md).
