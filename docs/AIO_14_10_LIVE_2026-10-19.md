# PS5 14.10 AIO live evidence — 2026-10-19

The Sony AIO syscall family is **callable in part** on the tested retail PS5 loader. This corrects the broad earlier conclusion that the whole family was inaccessible because syscall 661 stopped a worker. It does **not** establish a kernel vulnerability or the Relapse race.

**Confirmed data path:** The [95b one-byte completion capture](../results/phase17_new_vectors/95b_aio_one_byte_completion_20261019_195448.txt) goes beyond request IDs. It created socketpair fds 22/23, submitted an AIO read on fd 22 (ID `0x4205`), wrote `Z` to fd 23, polled state `3` (completed), and observed the read buffer change to `0xDEADBE5A`. Delete returned `0` with result `0`. This is direct evidence of a working read transfer through syscalls 669/664/662.

## Direct observations

- [86a section A](../results/phase17_new_vectors/86a_aio_real_handlers_20261019_194953.txt): syscall 670 default initialization returned `0` in PID 166. A later configuration attempt returned `-1`.
- [86a section B](../results/phase17_new_vectors/86a_aio_real_handlers_sectionB_20261019_195000.txt): syscall 669 returned `0` and wrote sequential request IDs `0x205`–`0x208`, including a request labeled invalid-fd. This proves ID publication, not successful I/O or a stale handle.
- [95a section B](../results/phase17_new_vectors/95a_aio_subsystem_sectionB_20261019_195100.txt): with a socketpair fd, read/write/per-item submissions returned `0` and IDs `0x209`–`0x20B`; zero count and invalid class controls returned `-1`.
- [95a section C](../results/phase17_new_vectors/95a_aio_subsystem_sectionC_20261019_195103.txt): another submission wrote ID `0x20C`. Syscall 664 polled it as state `1` (queued); syscall 666 cancellation returned internal result `4`; syscall 662 deletion returned internal result `0x80020010`; a later poll reported state `4`. Polling ID 0 gave `0x80020003`.
- [95c invalid-fd lifecycle](../results/phase17_new_vectors/95c_aio_invalid_fd_lifecycle_20261019_195516.txt): an invalid-fd submission still published ID `0x6205`; poll reported completed state `3` then `0x10003`, cancel result `3`, delete result `0`, and post-delete poll `0x80020003`. This does not prove stale-handle reuse or an I/O success on the invalid fd.
- [86a section C](../results/phase17_new_vectors/86a_aio_real_handlers_sectionC_20261019_195003.txt): delete/wait wrappers returned `0` but reported internal `0x80020003` for the tested invalid/empty input. The wrapper's success is not equivalent to operation success.

Initialization appears persistent for the game process: after the first successful `670`, subsequent init calls in the same PID returned `-1`. Thus [95a section A](../results/phase17_new_vectors/95a_aio_subsystem_20261019_195054.txt) and the first [95a section D](../results/phase17_new_vectors/95a_aio_subsystem_sectionD_20261019_195106.txt) cannot resolve first-time configuration. On fresh PID 79, [section D](../results/phase17_new_vectors/95a_aio_subsystem_sectionD_20261019_195443.txt) got `-1` from an invalid config and then `0` from default init, but it did not read back config group values; partial update remains unverified.

## Limits and next discriminating test

The captures now establish a completed one-byte read and show an orderly invalid-fd ID lifecycle. They do not show stale object use, memory corruption, privilege change, or the Relapse race. A readback method is needed for syscall 670's partial-update hypothesis. Do not interpret an internal status word as a kernel pointer or an exploit result.
