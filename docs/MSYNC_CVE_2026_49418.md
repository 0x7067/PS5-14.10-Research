# CVE-2026-49418 (device pager page-list use-after-free) on 14.10

A public write-up circulated on 2026-10-23 claiming that CVE-2026-49418 gives kernel
read/write on a PS5 through `msync(MS_INVALIDATE)`. This page records the advisory, the
mechanism, and what the call actually does on 14.10.

## The advisory is real

FreeBSD-SA-26:37.vm, "Use-after-free in device pager page list", announced 2026-06-30,
credited to `slidybat`. It affects all supported branches and is fixed in stable/15
`21929fbe1ced`, stable/14 `715831359fa7` and releng/14.4 `4c9e89c85d7c`.

The mechanism needs three steps in order:

1. map an **unmanaged device object** (a device pager mapping, `OBJT_DEVICE`);
2. call `msync(MS_INVALIDATE)` over part of it - the pages are marked invalid but stay on
   the pager's page list;
3. fault the same pages again - the fault handler re-inserts them, corrupting the list -
   and the object is destroyed, freeing a page twice.

The advisory's own impact note limits the consequence to "fictitious pages" that are never
recycled for another purpose, so a successful trigger is a use-after-free, not a turnkey
escalation.

## The syscall number

`msync` is **65**, with `narg = 3` in the 13.60 capture (`0xffffffff8b478af0`). Number 226
is the shared nosys stub (`0xffffffff8af220e0`, `narg = 0`), which is what PR #70 corrected
and what the 400-676 walk reproduces: under `SIGSYS` ignored, 226 returns `-1` and never
reaches a handler.

Probe 58a, written before that correction, would have measured the stub. It also rebuilds
the mapping address through `to_num()`, which truncates to 32 bits, and it defines
`MS_SYNC = 0` where FreeBSD's value is `4`, so the flag sets it sends are not the ones it
claims.

## What 14.10 does with the flags

`455a`-`455d` call 65 with the flag matrix on every kind of mapping a game process can
create. `-1` below is `0xFFFFFFFFFFFFFFFF`.

| mapping | 0 none | 1 ASYNC | 4 SYNC | 2 INVALIDATE | 3 ASYNC\|INV | 6 SYNC\|INV | 8 (unused bit) |
|---|---|---|---|---|---|---|---|
| anonymous, prot 3 | 0 | 0 | 0 | -1 | -1 | -1 | 0 |
| GPU-shaped, prot `0x33` | 0 | 0 | 0 | -1 | -1 | -1 | 0 |
| `/dev/dmem0`, `MAP_SHARED` | 0 | 0 | 0 | -1 | -1 | -1 | 0 |
| `/dev/gc`, `MAP_SHARED` | 0 | 0 | 0 | -1 | -1 | -1 | 0 |
| `/app0/eboot.bin`, `MAP_PRIVATE` prot R | 0 | 0 | 0 | -1 | -1 | -1 | 0 |
| `/app0/eboot.bin`, `MAP_PRIVATE` prot RW | 0 | 0 | 0 | -1 | -1 | -1 | 0 |
| `/savedata0/MAIN.LUA`, `MAP_PRIVATE` prot R | 0 | 0 | 0 | -1 | -1 | -1 | 0 |

Two facts come out of it. First, the call is `msync`: the accepted sets are exactly
`MS_ASYNC` and `MS_SYNC`, which is what a handler with the FreeBSD signature does. Second,
**`MS_INVALIDATE` is refused with `EINVAL` for every object type, not just device ones** -
vnode-backed mappings of a game file refuse it the same way. The unused bit is ignored
rather than rejected.

The device rows matter most: `/dev/dmem0` and `/dev/gc` both accept `mmap(MAP_SHARED)` and
produce real device mappings, which is the exact object the advisory needs, and the call
that would start the corruption returns `EINVAL` before any page is touched.

## Conclusion

On 14.10 the vulnerable branch is not reachable through the public interface: `msync` with
`MS_INVALIDATE` never succeeds, so no pages are marked invalid and the page list is never
corrupted. The claim that this CVE yields kernel read/write on the console is not supported
by any measurement here.

This does not prove the kernel contains the fix - the refusal could be a policy check in
front of a vulnerable body - but nothing a game process can call reaches it.
